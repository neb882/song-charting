## Findings, most severe first

**1. (moderate, reproduced) A song the friend charted and installed under v0.1.0 comes back as a second entry in
Clone Hero when he re-charts it.** M5-06 raised the library folder's name from 40 to 80 characters, and
`clonehero.install` replaces an older chart only when `songs/<name>` exists with that exact name (clonehero.py,
"A folder of that name there already"). Any song whose "Artist - Title" runs past 40 characters gets a new folder.
The test song is one: v0.1.0 installed it as `Car Seat Headrest - Beast Monster Thing`, v0.2.0 installs
`Car Seat Headrest - Beast Monster Thing (Love Isn't Love Enough)` beside it, both with the same song.ini name, so
Clone Hero lists the song twice. Repro (`<shm>/advisor/repro_names2.py`, v0.1.0's and HEAD's `cache.safe_name`):
```
0.1.0 'Car Seat Headrest - Beast Monster Thing'
0.2.0 "Car Seat Headrest - Beast Monster Thing (Love Isn't Love Enough)"
```
Not a crash or a lost chart; a confusing song list, and the friend's own long-named songs do the same. Options:
have `install` also look for the v0.1.0 cut of the name (and any folder whose song.ini says charter = songcharter and
the same name/artist) and treat it as the older chart to replace; or say in the guide's update bullet that an older
chart of the same song may need deleting by hand. Worth adding to the owner's PC check (item 8): re-chart the test
song and install it.

**2. (moderate, judgement from the code) install.sh does not check that the old songcharter is closed.** The guide
and the notice say "close the songcharter window" first, but nothing enforces it: step 6 deletes `app/0.1.0` and
step 7 re-syncs `runtime/env` (the running 0.1.0 server's own Python and site-packages) while that server may be
charting. A chart started from the old page after that spawns a child that imports 0.2.0 code into a 0.1.0
server, untested. The friend recovers (the new start says "songcharter 0.1.0 is still running ... close the
songcharter window", M5-12 item 4), but a chart under way at that moment is at risk. A cheap guard: before step 6,
`curl -fs http://localhost:8765/api/hello` (the server's port) and fail with "close the songcharter window first".
If not fixed, the owner's PC check should try the update once with the window open and see what happens.

**3. (low, judgement) The gate's CI step (M5-00 section 7, item 6) is not yet shown on c71009f.** Run 42202600033 was
in progress when I looked (Windows green, Linux running); the earlier run on the same commit was cancelled. Item 8
should wait for it, since 75-update.sh is the only end-to-end test of the path the friend takes.

**4. (low, judgement) Three decisions "left for the gate" are still open in PROGRESS:** the HOPO mode (the shipped
default is `forced`), the solo share on songs with vocals, and the CPU retry's WSL default after A23. The chord
rule's drift away from the humans on two references (Lucretia guitar 0.18 -> 0.08 against 0.14-0.20; All the Small
Things bass 0.007 -> 0) also awaits the owner's confirmation (PROGRESS, deferred). None blocks the PC checks, but
each should be decided or explicitly deferred to M5-99 before publishing, so the release notes match the chart.

**5. (low, judgement) A failed first CUDA take gives a 1-take CPU chart.** With the 4-take default, a transient
VRAM failure on the probe take means "that take is used alone, not 3 more on the GPU" (M5-05): a lower-quality
chart with a warning rather than a retry of the three others on CUDA afterwards. The page says so, and A23
exercises it; worth the owner noticing the quality of that chart, since the friend's 4070 has less headroom than
the owner's 5070.

**6. (low) The update deletes `app/0.1.0` before the new environment is synced.** A network failure in step 7 leaves
no working songcharter until the same line is pasted again; the guide says to paste it again, so this is
acceptable, but there is no way back to 0.1.0 (by design: M5-99's updater).
